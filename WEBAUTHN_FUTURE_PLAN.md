# Keetar as a WebAuthn passkey provider

## Context

The motivation: keep passkeys in the same portable, self-owned KDBX file as everything else, rather than locked into Google/Apple's platform silo. There's no way to *extract* an existing platform passkey (private keys are non-exportable by design — that's the whole point of the spec), so this is scoped to **new passkeys going forward**: Keetar generates and holds the keypair itself from the moment a site's "create a passkey" flow runs, storing it in the vault like any other secret. A real, deliberate trade-off worth stating up front: this makes the passkey only as safe as the vault (same protection class as a password — decrypted only in the background service worker's memory, at rest it's encrypted in the KDBX file), not hardware-non-extractable the way a platform passkey is. That's the cost of the portability the user actually wants.

Mechanism: 1Password/Bitwarden/Dashlane do this today by having a content script monkey-patch `navigator.credentials.create()`/`.get()` in the page's own JS context before the site's code runs — there's no official extension API for registering as a selectable option in the browser's native WebAuthn picker (confirmed: `chrome.webAuthenticationProxy` exists but is gated to remote-desktop use, and monopolizes *all* WebAuthn traffic browser-wide while attached rather than coexisting as a picker option). This is real, if fragile — the W3C WebAuthn WG has an open issue acknowledging extensions are "forced to monkey-patch" today (w3c/webauthn#1976).

**Scope for this plan**: registration (`create()`) and assertion (`get()`) against a known `allowCredentials` list, ES256 (P-256) only, attestation format `"none"` (the simplest valid format — no separate attestation-signing key needed, what every software passkey provider uses). Explicitly out of scope: discoverable/resident-credential "usernameless" sign-in, attaching a passkey to an existing entry (always creates a new one), cross-device/hybrid transport. Interception is **off by default**, a Settings toggle turns it on — consistent with how biometric unlock is already tucked behind the gear icon rather than always-on.

## Architecture: the relay chain

A page's own JS can't reach `chrome.runtime` APIs, and the isolated-world content script can't reach the page's `navigator.credentials`. Both hops, plus a UI surface for confirm/picker/unlock, are needed:

1. **MAIN-world shim** (new content script, `"world": "MAIN"`, no precedent for this in the repo today — first one) — monkey-patches `navigator.credentials.create`/`.get()`. On a `publicKey`-shaped call, captures the real arguments (rp, user, challenge, pubKeyCredParams, excludeCredentials/allowCredentials) and the true `window.location.origin`, and relays them via `window.postMessage` to the isolated world. Does **not** execute anything crypto-related itself — it only captures inputs and, later, resolves/rejects the original promise with whatever comes back.
2. **Isolated-world content script** (extends the existing `packages/web/src/autofill/content.ts`, or a sibling file in a new `src/passkey-provider/` module) — listens for that `postMessage` (validating `event.source === window`, since a malicious page could try to forge this channel), forwards the request to the background via the existing `KeetarRequest`/`KeetarResponse` union in `background/message-bus.ts` (content→background already flows through this exact union today — `LOGIN_FORM_DETECTED` is precedent, `content.ts:13`), gets back a `requestId`, and injects a small extension-hosted `<iframe>` overlay onto the page pointing at a new `passkey-prompt.html?requestId=...`. Also owns relaying the final result back to the MAIN-world shim, and rejecting the pending promise if the user closes the overlay without deciding.
3. **New `passkey-prompt` UI** (new HTML entry point, mirrors the existing `popup`/`options`/`manager` multi-entry pattern in `build/webpack.config.js` — adding a fourth entry point there is a small, well-trodden addition) — a small React page, full extension privileges since it's an extension-origin page loaded in an iframe. Fetches the pending request's (non-secret) details from the background, shows "Create/Use a passkey with Keetar for `rpId`?", handles unlock inline if the vault is locked (same `UNLOCK_VAULT` message the popup already uses), shows an entry picker for `get()` when multiple stored passkeys match the rpId (mirrors the existing match-and-pick shape in `autofill/matcher.ts` / popup's match list), and on confirm sends the actual `CREATE_PASSKEY`/`SIGN_PASSKEY_ASSERTION` message.
4. **Background** (`vault-session.ts`) does all the actual crypto and vault writes — the private key never leaves this process. Generates the ES256 keypair via WebCrypto (`crypto.subtle.generateKey`, extractable — needed to export into the vault, this is the exportability trade-off from Context), builds `authenticatorData` (rpIdHash + flags + signCount + attestedCredentialData for create) and the CBOR-encoded `attestationObject` (`{fmt: "none", attStmt: {}, authData}`), stores the entry, and returns only the public bytes (never the private key) back through the relay chain. For assertion, reads the stored key, signs, increments the stored counter, persists, returns the signature.

Manifest changes needed on both browsers: a new `"world": "MAIN"` content script entry (reusing the same `matches: ["http://*/*", "https://*/*"]` already granted — no new host-permission prompt), and `web_accessible_resources` for `passkey-prompt/passkey-prompt.html` (Firefox already has this key for `picker-callback.html`; Chrome's manifest doesn't have the key at all yet and needs the MV3 `{resources, matches}` array form added).

## Storage model

Reuse existing primitives, no new KDBX-level concepts:
- New KDBX **entry** per passkey (title = rpId or site name + " (passkey)"), created via the existing `Kdbx.createEntry`/`applyFields` path already used by `CREATE_ENTRY`.
- Private key: `entry.fields.set('KP_Passkey_PrivateKey', ProtectedValue.fromBinary(pkcs8Bytes))` — `ProtectedValue.fromBinary()`/`.getBinary()` (`packages/core/src/crypto/protected-value.ts`) is binary-native, exactly right for a raw PKCS8 key, no base64/string round-trip needed. Memory-protected in the KDBX4 XML automatically, same as Title/Password today (protection is decided purely by "is this a `ProtectedValue` instance", not a fixed field-name list — confirmed in `kdbx-entry.ts`).
- Metadata as plain custom string fields (not secret, no need to protect): credential ID (base64url), rpId, userHandle (base64url), COSE algorithm, sign counter (incremented on every assertion, same "background computes/updates, UI never touches it directly" shape as the existing TOTP counter precedent in `getEntryTotp`, `vault-session.ts:223-230`).
- A CBOR encoder does not exist in the repo yet (checked — no dependency, nothing hand-rolled). WebAuthn only needs a narrow CBOR subset (definite-length maps, byte strings, text strings, small integers), so this should be a small hand-rolled module (`passkey-provider/cbor.ts`) rather than a new npm dependency — consistent with `@keetar/core` already hand-rolling the KDBX binary format itself rather than depending on a generic library.

## New files (representative, not exhaustive)

- `packages/web/src/passkey-provider/page-shim.ts` — the MAIN-world `navigator.credentials` monkey-patch.
- `packages/web/src/passkey-provider/content-relay.ts` — isolated-world listener + iframe injection + result relay (or folded into `autofill/content.ts` if it stays small).
- `packages/web/src/passkey-provider/cbor.ts` — minimal CBOR encoder for `attestationObject`/COSE keys.
- `packages/web/src/passkey-provider/webauthn-crypto.ts` — keygen, `authenticatorData` construction, signing. Lives in `packages/web`, not `@keetar/core` — this is WebAuthn/browser protocol logic, not KDBX file-format logic, so it doesn't belong in core.
- `packages/web/src/ui/passkey-prompt/` — new React app + `passkey-prompt.html`, following the `ui/popup/`, `ui/options/` structure exactly.
- New `KeetarRequest`/`KeetarResponse` variants in `message-bus.ts` (stash pending request, fetch pending request details, list matching passkeys for a rpId, create, sign) plus their `background/index.ts` handlers and `vault-session.ts` methods — same pattern as every other message added this session (e.g. `APPLY_AI_SORT`, `SEARCH_ENTRIES`).
- Manifest edits in both `manifest.chrome.json` and `manifest.firefox.json`.
- A Settings toggle (Options page) to turn interception on, off by default.

## Security requirements (not optional, must land with v1)

- **rpId validation**: the browser normally enforces that a page can only claim an rpId that's a registrable-domain match for its own origin. Since we're intercepting *before* native validation runs, Keetar becomes responsible for this check itself — must validate `rpId` against `window.location.origin` (captured by the MAIN-world shim, not something a page argument can spoof) using the same suffix-matching rule WebAuthn specifies, or a compromised/malicious page could get Keetar to sign for a domain it doesn't own.
- **Bridge message authentication**: the isolated content script must not trust `window.postMessage` data at face value — verify `event.source === window`, and treat the MAIN-world shim as reporting real user-triggered browser API calls, not arbitrary page-supplied claims. This is the exact caveat the W3C WebAuthn WG thread flags about this whole technique.
- Origin/challenge used to build `clientDataJSON` must come from values captured at the moment of interception (isolated content script, a trusted context), never reconstructed later from something a less-trusted layer reports.

## Open question: hooking into native OS-level credential providers

Everything above makes Keetar show up via **in-page script interception** — it works, but only inside the browser Keetar is installed in, and it's invisible to the OS's own system-wide "Choose a passkey" picker (the one that appears from a native app, a different browser, etc.). Getting into *that* picker is a materially different, much bigger undertaking, confirmed by direct research into how 1Password and Bitwarden actually do it:

- **macOS/iOS**: requires a native Swift `ASCredentialProviderViewController` App Extension (`AuthenticationServices` framework, `prepareInterface(forPasskeyRegistration:)`), shipped inside a signed host app, gated by the `com.apple.developer.authentication-services.autofill-credential-provider` entitlement (macOS 14+/iOS 17+). No WebExtension API reaches this at all.
- **Windows**: a new (GA'd November 2025) native plugin model — implement the `IPluginAuthenticator` COM interface, register via `WebAuthNPluginAddAuthenticator`, packaged as MSIX (1Password's own Windows integration specifically required the MSIX build to register). No WebExtension path.
- **Android**: a native Kotlin/Java `CredentialProviderService` (Jetpack `androidx.credentials`), declared in an installed APK's manifest, Android 14+. No WebExtension path.
- **Linux**: no equivalent hook exists at all — the closest thing (freedesktop.org Secret Service / `libsecret`, used by GNOME Keyring / KDE Wallet) is generic secret storage, not a WebAuthn-aware system picker.

Bitwarden's own architecture docs state this outright: "there are currently no browser APIs that allow extensions to provide passkeys alongside the browser's native implementation." Both 1Password and Bitwarden's actual system-wide passkey support comes from **separate native apps per platform** (Swift, C++/C#+COM, Kotlin) that register with the OS and talk to the browser extension over local IPC — the native app is the primary integration point, the browser extension is a thinner client alongside it.

What this means for Keetar: system-wide OS-picker presence is not an extension feature — it would mean shipping and maintaining three separate native codebases (macOS/iOS, Windows, Android), each with its own signing/notarization/store-review burden, sharing vault access with the browser extension via local IPC (or by both reading the same KDBX file directly). That's a different-shaped project from the rest of Keetar, not an incremental extra on top of the plan above. Worth deciding deliberately, later, rather than assuming the in-page-interception version is a stepping stone toward it — it mostly isn't; the two integrate with the world in fundamentally different ways.
